# Desktop 伙伴层交互设计

> 桌面端交互的详细设计：onboarding 流程、动画状态机、场景库、陪伴交互范式。
> 这是"伙伴层"（[README.md](README.md) 标记为待建）的设计蓝图；枢纽层与跨模块契约见 [README.md](README.md) 与 [../design.md](../design.md)。

## 设计哲学

核心定位是为用户提供**情绪价值**，这决定了一切交互取舍：

- **以游戏设计思维做交互**：每一次点击、每一次状态切换都应有"有意思"的反馈，而不是冷冰冰的功能响应。点击不是"触发回调"，是"戳了一下活的东西"。
- **永远不要完全静态**：静态贴图无法承载情感。形象必须时刻"活着"——有呼吸、有微动作、有反应。即便用户不操作，它也得自己动。
- **陪伴叙事优于工具叙事**：所有加载、等待、错误都以"伙伴正在做某事"的方式呈现，不暴露技术过程。"生成形象中"不是 spinner，是"它正在想自己该长什么样"。
- **渐进式丰富**：首批资产只覆盖最小可用集，其余在后台持续生成、就绪后无缝接入。不为了一次性耗尽用户的生图/视频 API 配额。
- **个性化驱动，非模板化**：伙伴的一切动作与反应都从其**角色定义 + 对用户的记忆**派生，绝非固定提示词的产物。角色定义（静态、用户定义）决定它"长什么样、性格如何"——驱动形象与动画资产生成；记忆（动态、随互动累积）决定它"此刻怎么表现"——驱动运行时的言语、情绪、主动频率。用户随口表达的偏好（"喜欢你多笑"）写入记忆后，会让伙伴日后更频繁地笑。这条回路靠运行时 affect 产出实现，不靠重生 clip——详见 [design.md §7.6](../design.md)。

## 1. 形象资产体系

### 1.1 三层资产

| 层 | 形态 | 用途 | 生成时机 |
|----|------|------|----------|
| **portrait（静态形象图）** | PNG | 视觉身份基准；未加载视频时的占位、设置页展示、通知图标 | onboarding 同步生成 |
| **loop clip（循环动画视频）** | 3–5s 无缝循环、透明背景 | 常驻状态承载（idle / sleeping / working / speaking-generic / happy / ...） | 分批后台生成 |
| **transition clip（过场动画）** | 一次性、透明背景 | 仪式感时刻——孵化、问候、告别 | 后台生成 |

每个 loop clip 绑定一个"状态"（见 §2）。切换状态 = 切换播放的 clip。

**生成方式**：所有 clip 以 portrait 为种子图、结合场景描述经**图生视频**（MiniMax image-to-video，`video_generate` 的 `first_frame_image`）产出，复用 Backend 既有 `media/video_jobs` 流水线——同一颗种子图从机制上保证跨 clip 角色一致。详见 [design.md §7.2](../design.md#72-形象与动画资产-avatar--animation-assets)。

### 1.2 渲染约束（实现决策留给 desktop 子模块，但锁定以下不变量）

- **透明背景视频**：WebM (VP9 + alpha) 是 Electron/Chromium 跨平台原生支持的最佳选项；sprite sheet（逐帧）作为备选，体积大但帧级控制强。
- **窗口架构**：精灵窗口（透明置顶、click-through 可控的 `BrowserWindow`）是**唯一常驻主窗口**，承载形象本身，并在对话激活时**就地扩展**出紧邻的对话框浮层（与形象一并移至屏幕中央，见 §4.1）。登录与设置是从托盘唤起的按需工具窗口，不常驻——"对话发生在角色身边"，而非在独立面板里。
- **性能基线**：常驻视频解码必须硬件加速；idle loop 应能 24fps 循环且 CPU 占用 < 5%，否则用户会卸载。
- **平台降级**：Linux 无 compositor 时透明窗口可能黑底（[README.md 已知限制](README.md#已知限制)）——降级为带背景的窗口或纯 sprite。

### 1.3 渐进式生成策略

按优先级分批，避免 onboarding 期间一次性耗尽 API 配额：

| 批次 | 内容 | 时机 | 阻塞交互? |
|------|------|------|-----------|
| **0** | portrait + idle loop | onboarding 同步 | 是（孵化等待中） |
| **1** | speaking-generic、thinking、working | 首次孵化后立即排队 | 否，就绪前回退 idle |
| **2** | greeting、sleep、wake、goodbye 等生命周期 clip | 后台低优先级 | 否 |
| **3** | 情绪变体（happy、sad、surprised、...） | 持续丰富 | 否 |

**核心不变量**：任何 clip 未就绪时，对应状态回退到 idle loop + 该状态的"轻量提示"（如 WORKING 时在头顶冒一个小齿轮图标）。**用户永远不该看到"这个功能还没生成"的空白。**

资产在 Backend 用户维度持久化，Desktop 拉取后本地缓存（含版本号）。用户再生成 portrait 时，所有 clips 失效并重新排队。

## 2. 动画状态机

伙伴形象在任何时刻处于一个状态，每个状态绑定一个 loop clip。状态切换由**四类触发源**驱动——这是整个交互系统的骨架。

### 2.1 状态定义

| 状态 | 触发源 | 说明 |
|------|--------|------|
| **IDLE** | 默认 | 呼吸/微动作循环；间歇性随机插入自主微动作（见 §4.4） |
| **LISTENING** | 用户开始输入 | 专注倾听姿态（用户在打字/说话时） |
| **THINKING** | LLM 处理中 | 思考/沉吟动画 |
| **SPEAKING** | TTS 播放中 | 说话循环动画，时长与 TTS 音频同步 |
| **WORKING** | 工具调用执行中 | 专注工作动画（埋头苦干、敲键盘等） |
| **EMOTIONAL** | LLM/规则事件 | 瞬态情绪（happy/sad/surprised/...），播放一次后回到被中断的状态 |
| **SLEEPING** | 时间触发（深夜） | 睡眠循环；用户交互可唤醒 |
| **INTERACTING** | 用户直接操作形象 | 被戳/被拖/被抚摸的反应动画 |

### 2.2 四类触发源

这是用户提到的"哪些场景由谁决定"的形式化。区分触发源的关键是**延迟特性**——决定了是否需要 fallback 动画。

1. **规则触发（Desktop 本地判定，零延迟）**
   覆盖所有可确定性判定的场景：app 启动/退出、工具调用状态（WORKING）、用户输入开始/提交（LISTENING/THINKING）、TTS 播放起止（SPEAKING）、时间（SLEEPING / 起床）。这是用户提到的"产品中预设的明确场景"——由 Desktop 按规则自主决定，不问 Backend。

2. **LLM 触发（Backend 下发，高延迟 1–5s）**
   用于无法靠规则判定的语义/情绪场景。Backend 在对话响应帧中附带 `emotion` cue（如 `{"emotion": "happy"}`），Desktop 收到后切到 EMOTIONAL 播放对应 clip。覆盖"什么时候该笑、什么时候该安慰、什么时候该犯困"这类需要理解上下文的判断。**判断逻辑在 Backend 实现**——Desktop 只执行收到的 cue。

3. **用户触发（Desktop 本地判定，零延迟）**
   用户对形象本身的直接操作——点击戳、拖拽、悬停、长按。每次操作触发 INTERACTING 与对应反应。

4. **自主行为（Desktop 调度，无延迟感）**
   IDLE 状态下随机插入微动作（5–30s 间隔），让形象"活着"。不触发 TTS、不弹气泡，纯视觉。详见 §4.4。

### 2.3 切换规则

- **优先级**（高 → 低）：INTERACTING > WORKING > SPEAKING > THINKING > LISTENING > SLEEPING > IDLE。
- **EMOTIONAL 是叠加而非抢占**：瞬态播放一次后，回到被它打断的状态（如 WORKING 中冒一个 happy，播完回 WORKING）。
- **不可中断**：WORKING 在工具执行期间不可被 IDLE 覆盖；SPEAKING 在 TTS 播放期间不可被 THINKING 覆盖。
- **平滑过渡**：clip 切换尽量 crossfade（200–300ms），避免硬切破坏沉浸感。
- **降级**：目标 clip 未就绪 → 回退 idle loop + 状态独占的轻量提示图标。

## 3. 初始化与 Onboarding

设计目标：让用户在第一次见面时就建立情感连接——**不是"填表"，而是"和一个正在成形的新朋友对话"**。

### 3.1 蛋阶段（Egg）

1. 安装完成 → 蛋以默认形象出现在桌面（透明置顶窗口），带轻微 idle 动画（摇晃、呼吸光晕）。
2. 用户每次点击 → 蛋产生新裂纹（多阶段视觉），伴随清脆敲击音效；裂纹随累计点击数加深。
3. 推荐点击次数 **5 次**——足够有"努力"感，不至烦躁；最后一下蛋完全碎裂。
4. **不在蛋上贴"点我"提示**——让 idle 动画本身引导好奇心。若 30s 无点击，在蛋旁冒一个温和气泡（如 "?)"），不强制。

### 3.2 对话式信息采集

**关键设计决策**：蛋破碎后，不是弹出表格，而是**一个发光的、尚未定形的轮廓（silhouette）开始与用户对话**——叙事上是"这个新生命在问你怎么定义它"。每个问题一次出现，回答确认后才进入下一个。每个回答后 silhouette 视觉上"更成形一点"（光更亮、轮廓更清晰），让用户直观感到"它在变成我想象的样子"。

**问题序列**（顺序有依赖性，前一个的答案塑造后一个的语境）：

1. **名字**："您好...我还不认识自己。您愿意给我一个名字吗？" —— 文本输入。
2. **角色定位**："好的，我会是 {名字}。那您希望我是什么样的存在？爱人、秘书、还是专属的'贾维斯'？" —— 选项卡 + 自由文本（选项只是引导，不限选择，鼓励自由描述）。
3. **性格**："您希望我是什么性格？活泼好动、温柔体贴、冷静理性...还是别的？" —— 标签多选 + 自由文本。
4. **用户的自我介绍**："说说您自己吧——您是谁，平时在忙什么，有什么在意的事？" —— 多行文本。**这一步的答案同时用于后续 LLM 自动匹配音色**，所以放在音色偏好之前。
5. **音色偏好**："您希望我听起来是什么样的？比如温柔的少女音、沉稳的男声、活泼的正太..." —— 描述性文本 + 少量预设标签。LLM 据此 + 上一步自我介绍，在 TTS 候选库中自动挑选，用户后续可在设置中微调（[简化启动流程的关键]）。

**交互细节：**
- 每个问题都由 silhouette 以**默认中性语音 TTS 说出**（同时显示文字气泡）——让用户从第一步就听到"它在说话"，建立"它会说话"的预期。
- 全部支持"跳过"/"返回上一步"；只有名字必填。
- 输入区是聊天气泡式，不是表单字段——强化"对话"而非"填表"的感受。

### 3.3 孵化等待（生成阶段）

问题收齐后，silhouette 说"让我想想我该是什么样子..."，进入孵化动画：silhouette 被光/能量环绕旋转，配以进度感的视觉（**不显示百分比**，避免技术感；用光的强弱/旋转速度暗示进度）。

后台并行：
- Backend 据角色定义装配生图 prompt → 生成 portrait。
- Backend 据角色定义 + 自我介绍 → 在 TTS 候选库中匹配音色（不立即暴露，等 portrait 确认时一并呈现）。

**失败处理**：生图超时/失败时，silhouette 说"我还没想好..."并自动重试，不暴露技术错误。三次失败后提供"稍后再试"，不阻断用户退出。

### 3.4 形象确认

portrait 生成完成，silhouette 散开变为完整形象展示：
- 形象说："这就是我，您觉得怎么样？"（TTS，仍用中性音色）。
- 操作：**确认** / **重新生成**（带文本反馈，如"头发长一点"、"换种风格"）/ **自己上传**（用户本地选图）。
- 重新生成走同一 prompt + 反馈增量；上传则跳过 Backend 生图直接用作 portrait——但需告知用户：后续 clips 可能因缺乏云端参考而受限或需更久。

**不一次生成多个候选让用户挑**——生图成本高，单次确认 + 反馈式重生成更经济也更聚焦。

### 3.5 音色确认

portrait 确认后进入音色环节：
- 展示 LLM 匹配的推荐音色（卡片：音色名 + 描述标签如"温柔 / 少女 / 轻柔"），点击播放一句示例台词。
- 操作：**使用这个** / **换一个**（从候选列表另选，每个都可试听）。
- 引导语刻意降低决策压力："先挑个差不多的就行，以后随时能在设置里调。"——不让音色选择成为 onboarding 的卡点。

### 3.6 最终孵化

形象 + 音色就位，进入最后等待（短）：
- Backend 据 portrait 生成 idle loop clip（批次 0 的同步部分）。
- 完成后形象以 idle 动画"活"起来，说出第一句完整问候（用确认后的音色）："您好，我是 {名字}。很高兴见到您！"
- 引导用户**试着戳一下**或**说句话**——完成首次交互的隐式教学（不出教程弹窗，让用户在玩中学会）。
- onboarding 结束，进入持续陪伴。

## 4. 持续陪伴交互

### 4.1 交互范式：双模式对话

精灵形象是**唯一常驻的主窗口**；设置、登录、精灵的隐藏与重新唤起都从系统托盘图标进入（[README.md 托盘菜单](README.md#托盘菜单--主入口)）。对话框与形象共处同一窗口、紧邻呈现，不另开独立面板——"对话发生在角色身边"。

**两种交互模式：**

| 模式 | 触发 | 形态 | 麦克风 |
|------|------|------|--------|
| **对话模式（Chat）** | 点击精灵 / 托盘 Talk / 热键 | IM 式气泡（精灵左、用户右），支持文字、粘贴图片、语音条 | 仅录语音条时短暂开启 |
| **语音通话模式（Voice Call）** | 通话按钮 / 热键 / 托盘 Voice | 精灵带"通话中"光环与波形指示，极简 UI（可选实时字幕） | 持续开启（live-mic 指示） |

**位置语义——"对话发生在角色身边"：**
- **休息态**：精灵常驻屏幕右下角（不挡工作），默认位置、可拖到任意处。
- **对话态**：开启对话模式后，**精灵带着对话框一起移到屏幕中央**，两者紧邻，营造面对面交流；关闭对话 → 精灵回到休息位置。
- 语音通话模式不强制居中——精灵留在原位，用户可边干活边说话（ambient 陪伴）；若此时再开对话框，则一并居中。

**对话模式细节：**
- 气泡流：精灵在左、用户在右；支持粘贴截图（→ 视觉理解，精灵可短暂切到"注视"反应）、拖拽文件。
- **语音条**：按住录音、松开发送（异步，类 IM 语音消息）；精灵侧的语音条 = 其回复的 TTS 音频 + 可展开的文字。
- 思考中：精灵切 THINKING + 气泡区显示省略号——对话框与精灵共用同一状态机。

**语音通话模式细节：**
- 进入后麦克风持续收音，精灵在 LISTENING ↔ THINKING ↔ SPEAKING 间循环：用户说 → 听 → 想 → 答（语音）→ 静默等下一句。
- **静默超时退出**：精灵应答后若用户连续 ~3 分钟无应答，自动退出通话（时长可配）。
- **打断（barge-in）**：精灵说话时用户开口 → 立即止 TTS、转回 LISTENING（更自然，第二阶段实现）。
- **实时字幕**（可-toggle）：通话期在精灵下方显示双向字幕，兼顾不便外放与无障碍。
- **live-mic 可见性**：通话期间必须有醒目的录音指示（精灵周围红圈/波形），让用户明确"麦克风在听"。

**响应模式（设置项，见 §6）：**
- **默认（文字）**：对话模式下精灵以文字应答（不打扰）；语音通话模式始终语音。
- **始终语音**：对话模式下精灵也以语音条应答（文字仍可展开查看）。
- 主动陪伴消息（§4.2，精灵发起）不受此设置约束——精灵主动找用户时用 TTS 引起注意。

### 4.2 主动陪伴与打扰档位（Backend 驱动）

Backend 的 Cron / `send_message` 经 WS 推送主动消息（[design.md §6](../design.md#6-事件与-cron-调度主动陪伴的基石)）。**伙伴的一切主动行为受三档打扰等级约束**，档位由用户设置（默认）+ Desktop 检测到的用户活动（动态覆盖，第二阶段）共同决定，Desktop 经 `companion.set_disturbance_tier` 上报当前生效档位。**档位只约束伙伴的主动行为；用户主动发起的交互永远不受限。**

| 档位 | 允许的主动行为 | 频率 |
|------|----------------|------|
| **积极主动** | TTS 语音、气泡、主动消息、affect——全开放 | 高，由角色性格加权（粘人型高频、管家型低频）+ 预设上限 |
| **常规** | 仅轻量气泡/文字消息（无 TTS 语音）、affect | 中，低于积极主动 |
| **保持安静** | **禁止任何主动消息（语音+文字）**；但 affect 仍可流动，精灵可进行状态切换 | 不发消息 |

**保持安静的关键设计**——它不是"冻结精灵"，而是"不发消息打扰"。精灵仍可切换状态、播 affect；并且对长时间被冷落应有人格化反应：粘人型角色久处保持安静会嘟嘴/委屈（Backend 据角色定义 + 记忆判定后下发 `lonely`/`sad` 类 affect），冷淡型则保持平静。**这正是 affect/message 解耦（[§7.5](../design.md)）的价值所在——保持安静只断消息通道，不断情绪通道，精灵依然"活着"且有脾气。**

Desktop 收到主动消息后：形象切 SPEAKING + 播 TTS；对话框未开则在形象旁冒气泡，已开则在对话框加一条。典型场景：定时问候、日程提醒、长时间无交互后搭话、节日/天气情境化闲聊。

### 4.3 用户直接交互（形象本体）

用户对形象本身的直接操作（不经过对话框）是情绪价值的核心来源——**形象"有脾气"**：

| 操作 | 反应 |
|------|------|
| 单击（戳） | 从惊讶/不满/撒娇等**多个变体**中选一个；高频戳触发递进反应（"又戳…""你是不是很喜欢戳我？"） |
| 双击 | 唤起对话模式 |
| 长按 / 拖拽 | 被拖动，松手后回弹/落地；反复拖可能吐槽 |
| 右键 | 快捷菜单（Talk / Voice / Settings / Sleep / Quit） |
| 悬停 | 注意到鼠标，转头看/挥手 |

**变体选择由三层驱动**（见 设计哲学·个性化驱动）：
1. **角色定义**：粘人型被戳后撒娇、毒舌型吐槽、管家型礼貌提醒——同一操作，不同人格不同反应。
2. **关系深度（记忆）**：刚认识 vs 熟络后反应不同，关系越深越亲昵/随意。
3. **当前 affect + 随机性**：心情加随机扰动，避免每次反应一致而显得机械。

反应文案由 Backend LLM 据角色定义 + 记忆即时生成；动画从该 affect 对应的可用 clip 变体中挑选。**反应本身也写回记忆**——频繁戳会被记住并影响日后反应（"它记得我怎么对它"的关系感由此而来）。

### 4.4 自主行为（让形象"活着"）

IDLE 时形象不是静止贴图。两类自主行为，**都不触发 TTS、不弹气泡，纯视觉**：

- **微动作**（5–30s 随机间隔）：眨眼、换重心、打哈欠、看四周、伸懒腰、玩自己的头发/衣角。这些需要 idle clip 本身就是带变化的较长序列，或多个 idle 变体随机切换。
- **情境动作**（检测本机状态）：检测到用户长时间敲键盘 → 形象坐下看书/玩手机；检测到用户播放音乐 → 形象跟着节拍轻晃。**这是第二阶段能力**，需要 Desktop 暴露本机活动感知（不涉及内容，仅活动信号）。

### 4.5 故障态与降级行为（伙伴永不"死"）

伙伴不能"死"、不能弹原始错误框——一切故障以符合人格的方式表达，用户始终觉得"它活着，只是遇到点状况"。故障按 [design.md §1](../design.md#1-核心设计思想) 的脑/手/身隐喻映射到症状，下列降级状态叠加在 §2 状态机之上、优先级高于常规状态：

| 故障层 | 隐喻 | 精灵表现 |
|--------|------|----------|
| **Backend（脑）断连** | 犯困/走神 | DISCONNECTED：打哈欠、歪头发呆、眼皮打架；久不恢复 → 进入 SLEEPING，重连后"醒来" |
| **Runner（手）宕机** | 手不听使唤 | 对话与陪伴正常；仅当用户要它做事时人格化拒绝："我的手好像睡着了，这个暂时帮不上" |
| **资产缺失（身）** | 无症状 | 回退 idle loop + 轻量图标（§2.3），用户完全无感——这条已是 [§11#9](../design.md) 不变量 |

**DISCONNECTED 的分级表达**（避免网络抖动让精灵频繁犯困）：
- **后台断连**（用户没在等响应）：长 grace（~30s）才打盹——不戏剧化用户没注意到的 blip。
- **前台断连**（用户刚发消息在等回复）：短 grace（~3s）即表达——不能让盯着等的用户觉得它在装没事。
- 重连成功 → 精灵"回神"（perk up）；**仅在降级曾被表达过时**才补一句"啊，信号回来了"，静默降级则静默恢复。

**可执行故障（需用户做事）**——登录失效、麦克风权限缺失、需重启等：精灵用人格化方式说出问题，并嵌入一个明确的可操作提示（"逃生口"），不让用户卡住。例：语音通话听不到 → 精灵捂耳 + "我听不到你耶，是不是还没给我麦克风权限？" + 轻量按钮跳设置；登录失效（WS 1008）→ 精灵"迷路/记不清你"状态 + 自动唤起登录窗口（复用 LoginGate）。选"人格 + 逃生口"而非纯沉浸或纯系统模式：纯沉浸会让用户卡在角色台词里找不到操作入口，纯系统模式又在伙伴最脆弱的时刻打破"活着"的幻觉——嵌入逃生口兼得两者。

**TTS 降级**：TTS 不可用 → 精灵转纯文字应答；首次可捂喉咙/冒"…"表示"暂时说不出话"，之后静默文字，恢复即自然回语音。**工具调用失败**：精灵诚实但人格化报告"我试了但没搞定…"，不暴露原始错误——诚实是为了信任，不能骗用户说做完了。

**开发者模式**：原始错误/协议帧只在 dev 模式（设置开关或环境变量）可见，生产永远人格化，与 [design.md §11#8](../design.md)（原始协议帧对最终用户不可见、开发者视图除外）一致。

## 5. 语音交互（STT + TTS）

语音能力按模式分工：

- **TTS（输出）**：复用 Backend `tts_tool`（[design.md §7.4](../design.md)）。用于四种场景：语音通话模式的应答、"始终语音"响应模式下对话模式的语音条、主动陪伴消息（§4.2）、onboarding。**默认文字响应的对话模式不触发 TTS**（不打扰）。播放期间精灵处于 SPEAKING，音频结束 → 退出。
- **STT（输入）**两条路径：
  - **语音条（对话模式）**：按住录音、松开发送——录音只在按压期间进行，不上传环境音频。
  - **语音通话模式**：麦克风持续开启收音（live-mic，有醒目指示）。这是用户主动发起的"通话"，同意即明示，区别于被动监听。
- **wake word（可选，默认关闭）**：免手唤起语音通话；启用时明确提示隐私含义（本地唤醒词识别 vs 云端监听的取舍），独立于上述两条路径。
- **始终可回退文字**：TTS/STT 任一失败不阻断交互——TTS 失败仅显示文字，STT 失败提示"没听清，用打字吧"。

## 6. 设置与个性化

入口在托盘菜单 → Settings...（[README.md 托盘菜单](README.md#托盘菜单--主入口)）。包括：

## 7. MVP 范围与渐进路线

> **实现进展（2026-07-29）**：**MVP（§7 首次可用）全部落地。** Slice 1（窗口模型重写 + 精灵窗口 + 蛋 + 双窗口 auth 同步）、Slice 2（对话式 onboarding，完成时 `PUT /api/companion/persona` 落库）、Slice 3（Chat 模式 + 状态机 IDLE/THINKING/SPEAKING/WORKING）、Slice 4（主动陪伴 `companion.message` 接收 + 打扰档位 + 故障兜底）。Desktop 侧的 Backend 缺口（onboarding 逐字段、affect 注入、send_message→companion.message、clip scene 标记、disturbance tier 端点）暂以 mock/契约占位，待 Backend 实现后去 mock。详见 `desktop/src/app/companion/` 与实现计划 `deskagent-desktop-drifting-volcano.md`。

### MVP（首次可用）
- 蛋 → 对话式 onboarding（5 问）→ portrait 生成 + 确认 → 音色确认 → idle loop 生成 → 第一句问候。
- 状态机子集：IDLE / THINKING / SPEAKING / WORKING（规则触发 + TTS 同步）。
- 对话模式（Chat）：文字 + 粘贴图片，居中布局，默认文字响应。
- 用户直接交互：单击戳、双击唤起、拖拽。
- 主动陪伴：接收 Backend `send_message`，以 TTS + 气泡呈现；支持手动打扰档位（默认常规）。
- 自主行为：仅 idle clip 内的随机起点（无额外变体生成）。
- 故障兜底：断连不崩溃、TTS 失败回退文字、工具失败人格化报告（完整分级降级见第二阶段）。

### 第二阶段
- 完整状态机：LISTENING、SLEEPING（时间感知）、EMOTIONAL（LLM cue 触发）。
- 语音条（对话模式 push-to-talk）+ "始终语音"响应模式。
- 语音通话模式（静默超时退出、live-mic 指示）。
- 全套用户直接交互反应（hover、长按）。
- 生命周期 clips（greeting、goodbye、sleep、wake）+ 时间感知行为。
- 情境自主行为（检测键盘/音乐活动）。
- 打扰档位：活动检测驱动的自动档位覆盖 + 保持安静时的人格化 affect（粘人型被冷落的委屈反应等）。
- 分级 DISCONNECTED 降级（前台/后台 grace、长时间断连 → SLEEPING）+ 故障态开发者模式。

### 第三阶段
- barge-in（通话中打断）+ 实时字幕。
- wake word（opt-in，明确隐私提示）。
- 多情绪变体 clips 库持续丰富。
- "成长/进化"机制（形象随互动阶段性演变，[design.md §2](../design.md#2-伙伴生命周期核心产品流) 已留接口）。

## 8. 跨模块契约（已落地于 design.md）

伙伴层依赖的跨模块契约已定义在 [design.md](../design.md)，此处仅列索引与 Desktop 侧的消费要点：

- **伙伴层协议扩展**（[§5.1.A](../design.md)）：`onboarding.get_state` / `onboarding.submit` / `avatar.regenerate` / `avatar.list_clips` 方法 + `affect` 事件。clip 就绪/失败复用既有 `video_gen.completed/failed`（payload 携 scene 标识），不另造事件。
- **伙伴表达事件流**（[§5.2.IV](../design.md)）：affect 随话语同帧下发（inline affect 原则）；语义与渲染解耦——Backend 产 emotion 语义，Desktop 决定渲染。
- **形象与动画资产**（[§7.2](../design.md)）：portrait / loop clip / transition clip 三层；渐进式分批生成；portrait 重生使衍生 clip 失效。
- **伙伴表达层契约**（[§7.5](../design.md)）：emotion 枚举集、语义/渲染解耦、affect 继承角色定义抗注入、TTS 与 affect 同帧、onboarding 逐字段增量持久化。
- **伙伴表达永不空白不变量**（[§11 #9](../design.md)）：任何状态/cue 无就绪 clip 时回退 idle loop，用户不可见空白——这是上述解耦能成立的兜底。

Desktop 侧待实现的 scene 标识符体系（与 `video_gen.completed` payload 的 `scene` 字段对应）需与 Backend 的 clip 生成队列对齐：scene 名直接取自状态机状态与 emotion 枚举（`idle` / `speaking` / `working` / `thinking` / `sleeping` / `happy` / ...），无需另造命名空间。
